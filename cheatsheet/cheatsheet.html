Which Wins? Cheat sheet

Real code, raced on a real laptop. Two rounds each; the rule is what to remember.

No. 1Insertion Sort vs Merge Sortcounted steps
R1
Small lists (6 to 10 items)6 items: insertion 23 steps, merge 26. Insertion leads until the 10-item list
Insertion sort
R2
All nine lists, up to 256 itemsMerge 6,685 steps in total, insertion 44,591
Merge sort

Insertion sort (O(n²)) wins on tiny lists; merge sort (O(n log n)) wins as lists grow. Python's own sort uses both.

Interview: Why would a real sort use insertion sort at all? On a handful of items it does less work than merge sort, so libraries sort short runs with it and merge the runs (CPython's list sort does this).

No. 2Linear Scan vs Binary Searchcounted steps
R1
The first 1,629 stepsBinary search spends them sorting and finds nothing; the scan is already finding items
Linear scan
R2
Find all 64Binary 2,343 steps (sort included); scan 4,116. When binary finished, scan had found 34
Binary search

Search once: just scan. Search a lot: sort first, then binary search. That is why databases keep sorted indexes.

Interview: When is binary search not worth it? When you search only once or twice: sorting costs more than the scans you save. It pays off over many searches.

No. 3DFS vs BFScounted steps
R1
Reach the exitDFS after 75 cells checked, BFS after 136
DFS
R2
Find the shortest routeBFS's route is 35 cells (the shortest); DFS's is 57
BFS

Any way out: DFS. The shortest way: BFS. Over 3,000 mazes, DFS got out first in 94% and took the longer route in 94%.

Interview: Why does BFS always find the shortest path in an unweighted grid? It checks every cell 1 step away, then 2, then 3, so the first time it reaches the exit is by the fewest steps.

No. 4Dijkstra vs A*counted steps
R1
Junctions checked, MG Road metro to Indiranagar metro (Bengaluru)A* 746, Dijkstra 13,406

R2

A* adds one guess, the straight-line distance to the goal. It still finds the shortest route, with far less searching.

Interview: Why is A* still guaranteed the shortest route? Its guess, the straight-line distance, is never longer than the real road distance, so it never skips a shorter path.

No. 5O(1) vs O(2ⁿ)counted steps
R1
O(1), O(log n), O(n), O(n²) on 60 numbers1, 5, 60 and 1,770 steps
O(1)
R2
O(2ⁿ): try every subset of the 602⁶⁰ subsets: about 36.5 years at a billion a second
Nobody

The O tells you how the work grows: one more number doubles O(2ⁿ), adds about 120 steps to O(n²), and changes nothing for O(1).

Interview: Two numbers that add up to a target: how do you beat O(n²)? Remember the numbers you have seen in a dict and check for target minus x: one pass, O(n).

No. 6CPU vs GPUtimed
R1
Multiply two 4096 x 4096 matricesGPU 14 ms, CPU 162 ms: GPU 11x faster
GPU
R2
10,000 steps, each needing the step before (x = x * 0.999 + 1)CPU 36 ms, GPU 156 ms: CPU 4x faster
CPU

Work that splits into independent pieces goes to the GPU; work that runs step by step stays on the CPU.

Interview: Why do AI models run on GPUs? They are mostly huge matrix multiplies, where every output cell can be computed at the same time.

No. 7Sort All vs Heap of 10counted + timed
R1
ComparisonsHeap 1,000,419, sort 18,605,151: same top 10
Heap of 10
R2
Time in PythonHeap 21 ms, sort 151 ms (one laptop; times vary)
Heap of 10

For the top K of anything, keep a heap of size K: one comparison per item for most items. In Python: heapq.nlargest(10, scores).

Interview: Find the K largest numbers in a huge list. Keep a min-heap of K; replace its smallest whenever a bigger number arrives. O(n log K) instead of O(n log n) for a full sort.

No. 8Python vs Ctimed
R1
Add up the squares of 100,000,000 numbers in a plain loopC 63 ms, Python 3,882 ms: C 62x faster
C
R2
Same job, Python makes one NumPy call: np.dot(a, a)Python 34 ms, C's loop 63 ms
Python (NumPy)

A plain Python loop is slow; one library call that runs the loop in compiled code is fast.

Interview: Why is Python slow, and why is it still used for AI? The interpreter runs a loop one step at a time; the heavy loops in AI run in compiled code underneath (NumPy, PyTorch).

No. 9RAM vs SSDtimed
R1
Look up 100,000 records of 4 KB at random places in the same 1 GBRAM 46 ms, SSD 11,249 ms: RAM 245x faster
RAM
R2
The program holding the data is killed (kill -9)RAM: 0 bytes left. SSD file: all 1,073,741,824 bytes back, same checksum
SSD

RAM is fast but forgets; disk is slow but remembers. Real systems use both.

Interview: Why do databases write a log to disk before changing data? So that after a crash they can rebuild every change from the log; memory is wiped when the process dies.

No. 10Threads vs Processestimed

Interview: What is the GIL? In standard Python only one thread runs Python code at a time. Threads still help while waiting on files or the network, and they are cheap to start.

No. 11Index vs No Indextimed
R1
Find one user by email among 5,000,000With index 0.0031 ms, without 121 ms: about 39,000x faster
Index
R2
Add 1,000,000 new usersWithout index 507 ms, with index 920 ms: 1.8x faster; the index also doubled the file (191 MB to 381 MB)
No index

Lots of reads: add the index. Lots of writes: keep indexes few.

Interview: Why not index every column? Each index makes every insert and update slower and takes disk space.

No. 12Array vs Linked Listtimed
R1
Add up 10,000,000 valuesArray 5.3 ms, shuffled linked list 1,060 ms
Array
R2
Insert 2,000 values at the front of 200,000Linked list 0.002 ms, array 42 ms
Linked list

Arrays win at reading in order (the CPU fetches neighbours together); linked lists win at inserting at the front.

Interview: Why is a linked list slow to walk even though each step is O(1)? Its nodes are scattered in memory, so almost every step is a cache miss; an array's values sit next to each other.
